# Codex: остановка на обещании действия

Проверка 13 октября 2026 года подтвердила две составляющие проблемы: текстовое обещание завершает обычный ход Codex, а один из upstream-маршрутов не выдаёт вызов инструмента в формате Codex.

## Наблюдаемый случай

В локальной истории `01a13228-a908-7103-9f93-84c81842a840` модель `9router/glm-5.3-flash` несколько раз завершила ход обещанием следующего действия. В ходе от 01:26:05 МСК было девять вызовов инструментов, после которых последовал финальный текст «Обновил данные. Теперь добавлю production-снимок в пакет, обновлю README и создам commit». Продолжение началось только в следующем ходе. Это соответствует присланному скриншоту.

Также обнаружены ходы без вызовов инструментов, заканчивающиеся «Проверю…». Для этих сообщений `phase` отсутствует. Само отсутствие `phase` не доказывает потерю вызова: модель действительно может вернуть только текст.

Активная цель может инициировать следующий ход через механизм продолжения клиента. Без неё ответ, в котором нет нового вызова инструмента, завершает ход. Роутер не управляет состоянием цели в приложении.

## Проверка upstream

Для синтетического задания использован инструмент `exec`, печатающий маркер `ROUTER_PROBE_OK`. Проверка не исполняла команды из исследуемого чата и не меняла его историю.

| Маршрут одного и того же `apinex/free/glm-5.3-flash` | Вход | Результат live-пробы |
| --- | --- | --- |
| `/v1/responses` | `namespace` → `custom` → `exec` | `response.completed`, текстовое обещание и пример кода, без вызова |
| `/v1/chat/completions` | функция `exec` с аргументом `input` | структурированный `tool_calls`, `input` содержит JavaScript с маркером |

Добавка к инструкциям сама по себе не устранила первый сценарий. Пробы через выбранную модель `9router/glm-5.3-flash` обнаружили как `provider=glm`, так и `provider=apinex`, `model=free/glm-5.3-flash`; поэтому поведение выбранного имени зависит от фактического маршрута.

## Исправление

Для APInex запросы Responses с `custom`-инструментами или `namespace` направляются на Chat Completions. Проверяются объявления верхнего уровня, вложенные namespaces, `additional_tools` и история `custom_tool_call` / `custom_tool_call_output`. Используется существующий адаптер: он раскрывает namespaces, представляет freeform-инструмент как функцию с аргументом `input`, затем восстанавливает вызов инструмента и `namespace` в ответе Codex.

Обычные функции APInex без namespaces и запросы со stored-history ссылками продолжают использовать native Responses: Chat не умеет разрешать `previous_response_id` или `item_reference`. Codex-интеграция передаёт полную историю и уже запрещает такие ссылки. Другие провайдеры сохраняют свой выбор транспорта. В каталог внешних моделей добавлено пояснение, что обещание действия без вызова инструмента заканчивает ход, а необходимые вопросы и запросы разрешений допустимы.

При первой серверной приёмке `custom`-вызов успешно прошёл через production и локальный bridge, но в одном из трёх запусков настоящего Codex CLI модель остановилась на «Приступаю». Последующая трассировка показала, что CLI отправляет смешанный список обычных функций и namespace `collaboration`, даже без custom-инструментов. Поэтому нормализация расширена на namespaces; повторная приёмка должна проверять клиент целиком, а не только одиночный custom-вызов. Goal tools в повторном тесте явно отключены.

[OpenAI рекомендует сохранять `phase`](https://developers.openai.com/api/docs/guides/reasoning) для промежуточных и финальных сообщений. Native Responses passthrough сохраняет это поле; Chat Completions не имеет эквивалентного канала. Исправление не подменяет текстовые ответы искусственными промежуточными сообщениями и не создаёт цели автоматически.

## Проверка и пределы

Регрессионные тесты проходят реальный `handleChatCore`, проверяют URL транспорта, нормализованную схему, JSON/SSE-ответ, namespace и raw input. Опциональная live-проверка проходит два хода: настоящий upstream-вызов → восстановленный `custom_tool_call` → передача результата → финальный ответ с маркером.

```sh
/opt/homebrew/bin/node tests/node_modules/vitest/vitest.mjs run --config tests/vitest.config.js tests/unit/apinex-custom-tools-transport.test.js
RUN_REAL=1 /opt/homebrew/bin/node tests/node_modules/vitest/vitest.mjs run --config tests/vitest.config.js tests/unit/apinex-custom-tools-transport.test.js
```

Live-проверка использует существующий локальный integration state и его 9router API key, не выводя ключ. Она проверяет исправленный локальный handler через remote Chat Completions, а не развёрнутую новую версию сервера. Результат относится к проверенному upstream и моменту проверки. Модель всё ещё может самостоятельно завершить работу раньше времени; сохранение инструментального контракта не гарантирует выполнение произвольной задачи.
